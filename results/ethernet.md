# Ethernet on PROTEUS: a 10BASE-T MII transmitter in pure firmware

Measured, not projected. `firmware/ethernet_mii_tx.asm` (two 32-word programs)
is assembled by `tools/asm.py`, run on the cycle-accurate reference
`tools/model.py`, and decoded by an independent MII PHY model in
`demos/run_eth.py` that drives TX_CLK and samples TX_EN/TXD on every rising
edge. `python3 demos/run_eth.py` exits 0 with the tables below.

## Verdict

| question | answer | evidence |
|---|---|---|
| Can PROTEUS drive an MII PHY at 10 Mbit/s from firmware? | **yes** | 108 nibbles at 2.5 MHz, TX_EN framed, 80 ns setup / 240 ns hold, IFG 96 bit times |
| Can it compute the standard Ethernet FCS on-chip? | **yes** | CRC-32 bit-exact against `zlib.crc32` on 60, 64 and 200-byte frames; 140.8 cycles/byte |
| Can one engine emit a complete 802.3 frame incl. FCS? | **no** | 230 words measured for the emitter against a 32-word engine (7.2x) |
| Can it do 10BASE-T *on the wire* (Manchester, analog)? | **no** | no Manchester encoder, no PHY, no transformer: MII to an external PHY only |

The point of the exercise is the last two rows: a legal MII transmit stream and
a real CRC-32 are demonstrated, while the parts that do *not* fit are counted in
words instead of implied.

## Pin map (6 pads, all on `uio`, host SPI untouched)

| pad | direction | function |
|---|---|---|
| `UIO[0]` | input | **TX_CLK**, 2.5 MHz, generated by the PHY (20 `clk` = one nibble) |
| `UIO[1]` | output (side-set `CFG SIDE,0xC4`) | **TX_EN** |
| `UIO[2]` | output (`OUTP UIO,0x3C`) | **TXD0** (nibble bit 0) |
| `UIO[3]` | output | **TXD1** |
| `UIO[4]` | output | **TXD2** |
| `UIO[5]` | output | **TXD3** |

`uio[7:6]`, `ui_in`, `uo_out` are not driven, so the demo coexists with the host
interface. The 8-pin MII receive side (RXD\[3:0], RX_DV, RX_CLK, RX_ER) and
MDC/MDIO are not modelled at all.

## Timing (50 MHz clk, measured at the pads)

| quantity | value |
|---|---|
| TX_CLK period driven by the PHY model | 20 cycles = 2.5 MHz, 10 low + 10 high |
| nibbles in the stream | 108 (7x0x55 preamble, 0xD5 SFD, 46 payload bytes) |
| nibble order | bits [3:0] first, then [7:4]; TXD0 = LSB (802.3 clause 3) |
| per-nibble instruction budget | 20 cycles; the program uses 10-13 |
| TXD/TX_EN **setup** before the sampling edge | min 4 cycles = **80 ns** |
| TXD/TX_EN **hold** after the sampling edge | min 12 cycles = **240 ns** |
| TX_EN high window | one contiguous run over exactly the 108 sampled nibbles |
| IFG | 24 TX_CLK nibble times = 96 bit times = 4.8 us (802.3 minimum), then HALT |
| IFG timing basis | a fixed `WAITC 480`, i.e. a 4.8 us wait, not edge counting: correct while TX_CLK is the MII 2.5 MHz +-100 ppm, and it also survives a PHY that stops TX_CLK while idle |
| idle level after the frame | TX_EN = 0, TXD = 0000, pads held by the halted engine |
| pad contention / collision | none (`COLLISION = 0`) |

A write issued in cycle *c* appears on the pads in *c+1*; because TXD is only
ever written during a TX_CLK low phase there is no edge race, and the 4-cycle
worst-case setup (80 ns) is 8x the ~10 ns an MII PHY needs.

## Complete-frame budget: why the FCS is a second engine

There is no data memory. Every frame byte that is not generated by the counter
must be loaded as an immediate and shifted out, and each such byte costs a
measured **11 words** (1 `LDI` + 10 words for its two nibbles; the demo
assembles 4 bytes = 44 words and 5 bytes = 55 words to prove the slope).

| block | words |
|---|---:|
| engine 0 as shipped: CFG + preamble + SFD + 46-byte counter payload + IFG + HALT | **32** |
| + dst MAC, src MAC, ethertype (14 constant bytes x 11) | +154 |
| + FCS (4 constant bytes x 11) | +44 |
| **complete frame emitter, one engine** | **230 vs 32** |

Splitting does not rescue it:

* only one engine may own TXD/TX_EN (two writers on one pad is contention, not
  composition), so the emitter cannot be spread;
* the only inter-engine data path is the host FIFO (one byte per SPI frame), so
  a second engine can compute the FCS but cannot feed 60 frame bytes in
  20-cycle nibble time.

The FCS also cannot be computed *while* shifting out: 10 Mbit/s allows 40
cycles per byte of wire time and the bit-serial 32-bit CRC needs 140.8. It is a
**pre-transmit** computation -- 169 us for the 60-byte frame -- i.e. once per
frame at boot or during an arbitrarily long IFG.

## FCS values (measured)

Frame under test: dst `02 00 00 00 00 01`, src `02 00 00 00 00 02`, ethertype
`08 00`, payload `00 01 .. 2d` (46 bytes) = 60 bytes; with the FCS, 64 bytes,
the 802.3 minimum.

| quantity | value |
|---|---|
| FCS of that frame (IEEE 802.3) | `0xe7c87b32` |
| bytes on the wire, in order | `32 7b c8 e7` (LSB first) |
| firmware (engine 1, `r7:r4`) | `0xe7c87b32` |
| python `zlib.crc32` | `0xe7c87b32` |
| all-zero 64-byte frame | firmware `0x758d6336` = zlib `0x758d6336` |
| ramp 200-byte frame | firmware `0xed086180` = zlib `0xed086180` |

Parameters as implemented: reflected CRC-32, polynomial `0xEDB88320`, init
`0xFFFFFFFF`, final XOR `0xFFFFFFFF`, bits and bytes LSB first. The engine
applies the final XOR in firmware (four `NOT`s) and leaves the FCS in `r4..r7`,
`r4` being the first byte on the wire.

## Honest limitations

1. **No MAC header or FCS on the wire.** The shipped program sends preamble,
   SFD and the 46-byte payload: legal MII nibble traffic, *not* a legal 802.3
   frame. The missing 18 bytes are counted above (198 words).
2. **No receive path.** RXD/RX_DV/RX_CLK are neither sampled nor driven; no
   carrier sense, no collision detect, no jam, no backoff.
3. **No MDIO/MDC**, so no PHY configuration or link status.
4. **No Manchester encoding and no analog front end.** MII is already a
   digital 4-bit interface; the 10BASE-T PMD (Manchester, 2.2-2.8 V into
   100 ohm, transformer, squelch) is off-chip by construction. `research/
   protocols.md` §6.3/§6.4 reaches the same conclusion: the pads cannot do the
   analog side.
5. **No inter-frame pacing loop.** One frame per RUN; a continuous stream needs
   the host to restart the engine, or extra words for a loop plus a command
   handshake.
6. **FCS engine covers 1..255-byte frames** (8-bit length register). The
   64-byte minimum frame fits; a 1518-byte frame needs a 16-bit counter.
7. **Preamble/SFD are correct but the payload repeats the same 46 bytes**;
   there is no source address learning, no VLAN, no padding logic.

## Verification scope

Model-level only (`tools/model.py`, the executable reference the RTL must
match), on purpose:

* `sim/test_protocols.py` is out of scope for this task (the task's file list
  excludes `sim/`, `tb/` and `test/`), so no RTL row was added there.
* It would not be cheap anyway: every existing row of that suite is a pad model
  for a *chip-driven* bus. MII inverts the relationship -- the PHY owns
  TX_CLK and the chip is a slave to it -- so the testbench needs a new
  clock-generating pad model plus a nibble sampler. That is a testbench, not a
  row.
* Everything the firmware actually exercises (`WAITP` on an external pad,
  side-set on stall cycles, `WAITC`, `DJNZ`, `OUTP` masks) is already covered
  on the RTL by the existing suite, so the residual risk of a model/RTL
  mismatch in *this* firmware is the ISA surface, not the Ethernet logic.

The decoders share no code with the firmware: TX_CLK is generated outside the
chip, TX_EN/TXD are sampled on rising edges from the pad trace, and the FCS is
compared with `zlib.crc32`. Negative tests were run against perturbed firmware
(13-nibble preamble, `ROLI` instead of `RORI` for the high nibble, 45-byte
payload, IFG removed, a truncated CRC input); every one is detected.

## Reproduction

```
python3 demos/run_eth.py                              # exit 0, tables above
python3 tools/asm.py firmware/ethernet_mii_tx.asm     # 32 + 32 words
```

Word counts, as assembled by `tools/asm.py`: **engine 0 = 32 / 32**,
**engine 1 = 32 / 32**.
